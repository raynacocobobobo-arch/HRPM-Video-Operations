# HRPM 代码初步分析

## 结论

这份代码实现的是“恩万视频部项目人员一体化管理平台（HRPM）”。它不是传统意义上覆盖招聘、劳动合同、薪酬、社保、绩效的完整 HRIS，而是一套面向视频制作部门的项目排期与人力资源调度系统：以月份为单位，把项目、人员、每日任务、工种、时间段和项目成本联动起来。

本次收到的是一个 Base64 编码的 `tar.gz` 包。压缩包校验值为 `f497c56380a74026f64659bc256c8f1d28042ab0e44a7ea2481999b323b8305e`，内部只有两个普通文件，没有路径穿越或符号链接：

- `server.py`：2931 行，Python 后端，版本标注为 v3.51。
- `video_schedule_dashboard.html`：641 行，单文件前端页面。

Python 文件已通过静态语法编译检查；本次没有启动服务、导入公司数据或执行未知业务逻辑。

## 系统结构

### 后端

后端基于 Python 标准库 `http.server` 与 `ThreadingMixIn`，默认监听 `0.0.0.0:8765`。它没有使用 Django、Flask、FastAPI 或数据库 ORM。

HRPM 数据默认保存在：

```text
~/.hermes/crm/video-dept/video_schedule_data.json
```

写入时先生成备份，再写临时文件并使用原子替换，能降低文件写到一半损坏的风险。

### 前端

前端是原生 HTML、CSS、JavaScript 组成的单页管理台，通过 `fetch` 调用 `/api/video-schedule/*` 接口。没有构建工具、前端框架或独立依赖清单。

### 同一进程内的其他系统

`server.py` 不只承载 HRPM，还同时包含：

- 婚礼客户 CRM 与销售漏斗；
- 两家医院账号发布台账；
- 灯光库存页面、保存与历史版本恢复。

这些模块使用不同数据文件和部分独立登录，但共享同一个 Python 进程和端口。任何后端故障或安全问题都有可能扩大到其他业务模块。

## HRPM 的主要功能

### 项目管理

- 项目总览、项目表格和月度甘特排期；
- 项目编号、类型、负责人、金额、阶段、优先级和备注；
- 阶段包括未排期、筹备、拍摄、剪辑、修改、待交付、已交付、已回款和暂停/取消；
- 项目每日节点、子任务、跨日期拖动、复制到下月；
- 拍摄/后期的“安排”和“接收”状态；
- 项目删除、CSV 导出和跨月汇总。

### 人员管理

- 人员档案、全职/兼职/离职状态；
- 摄影、剪辑、包装、平面等角色；
- 电话、能力、风格、地址、全天/半天费率和备注；
- 忙碌、空闲、休假、待安排等实时状态；
- 按日维护多个时间段，支持拖动排期；
- 暂停人员和删除人员档案。

### 项目与人员双向联动

系统用 `link_id` 关联项目节点和人员任务：

- 在项目排期里安排人员，会同步到人员日程；
- 修改人员日程，会反向更新项目时间线；
- 删除或移动任务时，尝试同步清理另一侧记录。

这是整套 HRPM 最核心的业务逻辑。

### 成本计算

- 项目可维护人力、设备、差旅、运输和其他成本；
- 人员排期可根据全天/半天费率自动生成项目人力成本；
- 支持公司设备与自带设备的不同费率；
- 根据工作时长和午休判断半天或全天，也允许人工覆盖计费方式及金额；
- 锁定的人工成本不会被自动同步覆盖。

### 数据看板与导入导出

- 项目状态占比；
- 员工工作饱和度；
- 每日项目数与人员安排；
- 导入“视频部排期.xlsx”；
- 导入前备份旧 JSON，并尽量保留手工修改的负责人、阶段、金额、人员资料和人工排期；
- 导出项目 CSV 或整体表格。

## 当前代码包不是完整部署包

虽然消息标题写着“完整代码”，但压缩包仅有两个文件，无法单独完成部署。运行时还依赖以下未包含内容：

- `video_schedule_parser.py`：Excel 导入时动态加载；
- `video_schedule_data.json`：实际 HRPM 数据；
- `dashboard_live.html` 及婚礼 CRM 数据文件；
- 医院发布台账页面与数据；
- 灯光库存页面与数据；
- 部署脚本、服务配置、依赖说明和使用文档。

它更像是“当前后端主文件 + HRPM 前端页面”的源码快照，而不是可复现、可测试、可部署的完整项目仓库。

## 需要优先处理的风险

### P0：账号和网络安全

- 源码内存在明文、固定登录凭据，以及额外的兼容登录账号。报告不记录具体值，但这些凭据应立即轮换，并迁移到安全配置或密钥管理中。
- 服务默认监听全部网络接口；如果端口暴露在公网或办公网，风险很高。
- Cookie 缺少完整的 `Secure`、`HttpOnly` 等保护，未看到 CSRF 防护。
- JSON 响应统一允许跨域，部分婚礼 CRM 与库存接口明确免登录，其中还包含写入与版本恢复操作。
- 系统处理员工电话、地址、费率、项目金额等敏感信息，目前缺少细粒度权限控制和审计记录。

### P1：数据一致性和可靠性

- 多线程服务器会并发执行“读取整个 JSON → 修改 → 写回整个 JSON”。虽然写入是原子的，但没有文件锁或事务，两个用户同时保存时可能发生后写覆盖先写。
- 登录会话只保存在内存集合中；进程重启后全部失效，也没有持久化会话管理、用户表或角色权限。
- 备份持续累积，未看到保留周期和自动清理策略。
- 多数异常直接把 `str(e)` 返回给前端，可能泄露服务器路径和内部细节。

### P1：上传与前端输入

- Excel 上传只按文件扩展名判断，未看到上传大小、压缩包结构或资源消耗限制。
- 页面大量使用动态 `innerHTML`。代码提供了转义函数并在多处使用，但仍需逐个检查所有模板，确认没有存储型 XSS 漏洞。

### P2：工程可维护性

- 2931 行后端和 641 行单页前端高度集中，HRPM、CRM、医院发布和库存互相耦合。
- 没有测试、数据模式定义、迁移脚本、依赖清单、版本化 API 或正式部署说明。
- 人员名单、角色顺序、别名和部分业务规则直接写在代码里，人员变化需要改源码。

## 建议的完善顺序

1. 立即轮换所有源码中的固定凭据，限制端口访问，补 HTTPS、安全 Cookie、CSRF 和接口鉴权。
2. 把 HRPM 与婚礼 CRM、医院台账、库存拆成独立模块，先保持功能不变。
3. 将人员、项目、排期、成本迁移到带事务的数据库，并增加并发写测试。
4. 增加用户、角色、权限和操作审计；将费率、手机号、地址设置为受限字段。
5. 补齐 Excel 解析器、数据模式、部署配置、备份恢复说明和自动化测试。
6. 在安全与数据层稳定后，再优化交互、统计与新功能。

## 当前判断

从业务设计看，这套系统已经覆盖视频部门项目与人员协同的主要工作流，尤其是双向排期和自动成本同步，方向是对的。它目前更像一个快速迭代出的内部业务工具，而不是已经完成安全与工程化治理的生产级人力系统。后续完善应优先保住现有业务规则，同时先解决凭据、权限、并发写和模块耦合问题。
