# Video Operations 开源组合系统设计规格

日期：2026-09-01  
状态：设计已确认，实施尚未开始  
部署范围：目标为新的 Apple Silicon Mac，本机单用户

## 1. 目标

将现有 HRPM 从“项目表、人员表和排期表”升级为视频部项目经营与资源决策系统。新版不以原 HRPM 代码为基础重写，也不照搬某个开源系统的界面，而是直接组合成熟 GitHub 项目：

- OpenProject 负责项目、阶段、工作包、依赖、工时、预算和审计。
- Video Operations 插件补充视频行业人员、技能、档期、费率、阶段门和中文决策界面。
- Timefold Solver 负责人员与任务的约束排程。
- ERPNext 不进入第一阶段；未来只在需要正式采购、发票、回款和会计利润时接入。

系统的管理闭环为：

`项目准入 → 模板化拆解 → 阶段门 → 资源排程 → 执行反馈 → 成本预测 → 交付复盘 → 更新估算经验`

## 2. 已确认约束

- 系统只运行在这台 Mac，只监听 `127.0.0.1`。
- 当前只有用户本人操作；人员不需要注册系统账号。
- 用户只使用一个中文网站，不进入多个开源系统分别操作。
- 可以在后台运行多个开源服务。
- Excel 只用于一次性导入和按需导出，不做双向同步。
- 自动排程不能直接覆盖正式档期，必须经过人工确认。
- 冲突可以被人工强制保留，但必须填写原因并持续显示异常。
- 婚礼 CRM、医院发布台账和灯光库存不在本次范围。
- 原 HRPM 只作为历史数据来源，迁移完成后停止双向维护。

## 3. 范围

### 3.1 第一版包含

- 项目组合与七阶段视频制作流程。
- 阶段门检查、阻塞原因和变更记录。
- 人员、岗位、技能、可用时间和费率。
- 拍摄时间块与后期每日产能两种排程模式。
- Timefold 排程建议与日历前后对照确认。
- 计划成本、实际成本、完工预测和项目经营毛利。
- 异常驱动工作台、项目详情、档期、工时、成本和报表。
- 原 HRPM 与 Excel 一次性迁移。
- 本机备份、恢复和审计记录。

### 3.2 第一版不包含

- 多用户权限、审批层级、企业 SSO 和移动端 App。
- 婚礼 CRM、医院台账、灯光库存和通用资产管理。
- ERPNext 会计、发票、回款、采购和正式财务报表。
- 对外网访问、云同步和异地协作。
- 无人工确认的自动排程写入。
- 在 Plane、Leantime、Kimai 和 OpenProject 之间复制或同步同一批项目数据。

## 4. 开源组合与复用边界

### 4.1 OpenProject

仓库：[opf/openproject](https://github.com/opf/openproject)  
许可证：GPL-3.0

OpenProject 是运行中的项目管理主系统，而不是仅供参考。系统直接复用它的项目、工作包、关系、时间计划、工时、预算、活动日志、API 和 PostgreSQL 数据模型。

Video Operations 插件以官方 [opf/openproject-proto_plugin](https://github.com/opf/openproject-proto_plugin) 为结构起点，使用 OpenProject 的 Rails 插件机制和前端扩展机制。插件不修改 OpenProject 核心业务代码；需要定制的内容通过独立插件和自定义镜像交付，以便后续升级上游版本。

### 4.2 Timefold Solver

仓库：[TimefoldAI/timefold-solver](https://github.com/TimefoldAI/timefold-solver)  
示例：[employee-scheduling quickstart](https://github.com/TimefoldAI/timefold-quickstarts/tree/stable/use-cases/employee-scheduling)  
许可证：Apache-2.0

排程服务以 Timefold Community Edition 和员工排班示例为基础，增加视频行业的时间、地点、技能、岗位、产能、成本和锁定规则。Timefold 作为独立无状态服务运行，不保存正式业务数据。

### 4.3 暂不组合的项目

- ERPNext：财务闭环强，但第一阶段会与 OpenProject 的项目、工时和预算形成重复主数据。
- Plane：项目执行界面现代，但与 OpenProject 功能重叠，且引入另一套 Django、React、PostgreSQL、Redis 和队列服务。
- Kimai：工时和费率成熟，但 OpenProject 已提供第一阶段所需的工时与成本基础。
- Leantime：目标、风险和复盘理念纳入设计，但不运行第二套项目主库。

这些项目的管理经验可以影响流程设计，但第一版不复制其源码，也不运行重复服务。

## 5. 系统架构

```text
浏览器
  │
  ▼
OpenProject + Video Operations 插件
  ├── 中文工作台与业务页面
  ├── OpenProject 项目、工作包、预算和工时
  ├── Video Operations 人员、技能、档期和排程记录
  ├── PostgreSQL 唯一主库
  └── 排程适配器
          │ 本机 REST，带数据版本号
          ▼
    Timefold 排程服务
          │ 返回候选方案，不直接写库
          └──────────────────────────────┘

未来可选：OpenProject → ERPNext 项目编号与财务单据接口
```

所有对外页面都由 OpenProject 与插件提供。Timefold 端口只允许本机内部访问，不单独暴露给用户。

## 6. 数据主权

### 6.1 OpenProject 管理

- Portfolio、Program 和 Project。
- 七阶段项目生命周期。
- 工作包、父子关系、前置依赖、截止日期和负责人。
- 计划工时、实际工时、预算和活动日志。
- 项目附件、评论、风险状态和阶段交付物。

### 6.2 Video Operations 插件管理

- `CrewProfile`：不要求登录的人员档案。
- `Role`、`Skill`、`CrewSkill`：岗位、技能和熟练度。
- `Availability`：请假、不可用和偏好时间。
- `RateCard`：日、半日、小时和加班费率。
- `ResourceDemand`：工作包需要的岗位、技能、人数、时间和地点。
- `Assignment`：预占、锁定、完成或异常覆盖的人员安排。
- `ScheduleProposal`：排程建议摘要、输入版本和过期状态。
- `BaselineSnapshot`：项目准入时的日期、预算、工时和人员基线。
- `ChangeRequest`：范围、日期、成本和交付变化。
- `OverrideRecord`：强制冲突、原因、原值、新值和操作时间。

插件表与 OpenProject 使用同一 PostgreSQL 实例。插件通过 OpenProject 服务层和模型接口关联项目与工作包，不另建影子项目表。

### 6.3 Timefold 管理

Timefold 不拥有业务数据。每次求解只接收一个不可变输入快照，返回：

- 候选人员分配。
- 调整前后时间。
- 约束违反列表。
- 交付、负载和成本变化。
- 输入数据版本与方案评分。

## 7. 项目生命周期与阶段门

| 阶段 | 主要产出 | 通过条件 |
|---|---|---|
| 1. 项目准入 | 客户、类型、范围、交付日、预算和优先级 | 范围清楚、档期可行、预算可接受 |
| 2. 前期策划 | 文案、脚本、分镜、方案和资源需求 | 必需文件齐全并确认 |
| 3. 拍摄准备 | 通告、人员、设备、场地、交通和风险预案 | 无未处理硬冲突，关键资源锁定 |
| 4. 拍摄执行 | 素材、现场记录和备份 | 素材核验并完成双份备份 |
| 5. 后期制作 | 粗剪、包装、声音、调色、字幕和内审 | 内审通过，可提交客户 |
| 6. 审片修改 | 版本、客户意见和修改轮次 | 客户确认最终版本 |
| 7. 交付关闭 | 成片、源文件、归档、成本和复盘 | 交付确认且复盘完整 |

阶段门分为：

- 硬条件：缺失时不能正常进入下一阶段。
- 软条件：允许继续，但产生黄色风险提醒。
- 异常覆盖：用户填写原因后强制继续，保留永久审计记录。

项目健康度由进度偏差、资源冲突、成本偏差和确认阻塞自动计算。手工状态只能作为说明，不能替代计算结果。

## 8. 基线与变更管理

项目通过准入时锁定原始基线：

- 原始交付日期。
- 计划阶段与工作包工期。
- 计划人员与工时。
- 计划直接成本与目标毛利。

后续变化形成当前预测，不能覆盖原始基线。客户增项、补拍、增加修改轮次、交付日变化和预算变化必须生成 `ChangeRequest`，记录：

- 变化原因和发起方。
- 工期影响。
- 人员与档期影响。
- 成本和收入影响。
- 是否已批准。

## 9. 资源排程

### 9.1 双轨模型

- 拍摄与现场岗位按具体时间段安排，同时考虑集合、交通、地点、连续工作和休息时间。
- 剪辑、包装等后期岗位按每日小时产能安排，同时考虑截止日期、剩余工作量和关键路径。

### 9.2 安排状态

- 预占：容量预测，可由新方案调整。
- 已锁定：正式安排，自动求解默认不可移动。
- 已完成：保存实际人员、时间和成本。
- 异常覆盖：存在冲突但由用户强制确认。

### 9.3 硬约束

- 不安排明确不可用人员。
- 不重叠已锁定安排。
- 满足必要岗位、技能和最低人数。
- 拍摄地点之间保留交通时间。
- 满足每日最大工时和最短休息要求。
- 未通过拍摄准备阶段门的项目不能锁定正式拍摄。

自动建议不违反硬约束。人工可以强制覆盖冲突，但必须填写原因。

### 9.4 软约束优先级

1. 尽量不移动已确认安排。
2. 优先保护临近交付和关键路径任务。
3. 保持同一项目团队连续性。
4. 平衡人员负载。
5. 减少加班、跨地点奔波和碎片时间。
6. 在满足交付的前提下控制人工成本。
7. 尽量满足人员偏好。

### 9.5 人工确认

界面采用已确认的 D2 日历前后对照：

- 左侧显示当前整周排程。
- 右侧显示建议整周排程。
- 摘要显示冲突、延期风险、成本和负载变化。
- 用户只能整体应用或返回调整约束重新生成。
- 应用前再次验证输入版本；数据已变化则拒绝写入。
- 应用采用数据库事务，全部成功或全部回滚。

## 10. 成本与利润

### 10.1 成本基线

- 内部人员计划时间 × 内部成本费率。
- 外部人员和供应商费用。
- 场地、交通、住宿、餐饮和设备租赁。
- 其他直接支出和风险预留。

人员安排确认时保存费率快照。以后调整标准费率不修改历史项目。

### 10.2 三套数字

- 原始基线：项目准入时批准的计划。
- 当前实际：已发生的工时和直接费用。
- 完工预测：当前实际加剩余工作预计成本。

第一版计算项目经营毛利：

`项目收入 + 已批准增项收入 - 内部人工成本 - 外包费用 - 其他直接支出`

该指标不是正式会计利润。未来接 ERPNext 后，由 ERPNext 管理发票、回款和财务报表。

### 10.3 实际数据

当前由用户批量确认实际人员、时间、加班、补拍、支出和剩余工作量，不要求人员逐个登录填报。多人使用后再增加个人工时入口。

## 11. 中文网站信息架构

视觉决策结果：`A1 + N2 + P1 + D2`。

### 11.1 A1 聚焦处理工作台

首页主要显示：

- 立即需要决定的异常。
- 等待确认和今日到期事项。
- 无法通过阶段门的项目。
- 人员冲突和产能过载。
- 完工预测超基线的项目。
- 七天人员容量和本周拍摄摘要。

普通健康项目不占首页主要空间。

### 11.2 N2 对象式一级导航

- 工作台
- 项目
- 人员
- 档期
- 工时
- 成本
- 报表
- 模板与设置

### 11.3 P1 项目详情

项目默认页是当前阶段门，首先显示：

- 原始基线与当前预测。
- 当前阶段和七阶段进度。
- 阶段硬条件、软条件和阻塞项。
- 进入下一阶段的处理动作。
- 最近变更及其工期和成本影响。

任务、时间线、资源、成本、变更和文件作为项目内页签保留。

### 11.4 D2 排程确认

排程建议采用整周日历前后对照，并显示整体影响。只有用户确认后才写入正式排程。

## 12. 关键数据流

### 12.1 新建项目

1. 用户创建项目并选择视频项目模板。
2. OpenProject 生成阶段与工作包。
3. 插件创建原始基线和资源需求。
4. 项目通过准入后，阶段与基线锁定。

### 12.2 运行排程

1. 插件读取工作包、资源需求、人员、可用性和锁定安排。
2. 创建带版本号的输入快照。
3. Timefold 返回候选方案。
4. 插件生成 D2 前后日历与影响摘要。
5. 用户确认时再次检查数据版本。
6. 事务写入全部安排并保存审计记录。

### 12.3 记录实际与复盘

1. 用户批量确认实际人员、时间和费用。
2. 系统更新实际成本与完工预测。
3. 项目交付后生成计划与实际对照。
4. 系统提出模板工时和成本调整建议。
5. 用户确认后才更新模板。

## 13. 失败处理

- Timefold 不可用时保留手工排程能力，不丢失数据。
- 过期建议方案禁止写入并提示重新计算。
- 应用排程失败时完整回滚。
- 请求使用唯一幂等编号，避免浏览器重复提交。
- 页面关闭后可以查询上次请求最终状态。
- 强制冲突持续出现在异常工作台，直到解除或项目关闭。
- 错误信息必须说明对象、原因和可执行的恢复动作，不能只显示通用失败。

## 14. 安全与本机边界

- 所有对外监听绑定 `127.0.0.1`。
- Timefold 只接受插件所在主机的请求。
- API 密钥和数据库凭据不写入仓库。
- OpenProject 原生日志和插件审计共同记录关键变更。
- 当前只有一个管理员账号，不实现多角色权限。

## 15. 迁移

- 原 HRPM 和 Excel 采用一次性导入。
- 导入分为解析、校验、差异预览、人工确认和写入五步。
- 差异预览显示新增、更新、重复、缺失引用和无法识别记录。
- 导入不自动删除目标数据。
- 每次导入保存来源、时间、记录数量和失败明细。
- 完成验收后，原 HRPM 改为只读归档。

## 16. 备份与恢复

- 备份 PostgreSQL、项目附件和插件配置。
- 保留 7 份每日备份和 4 份每周备份。
- 备份目标优先使用另一块磁盘；同盘备份不能作为唯一恢复手段。
- 提供恢复脚本并记录恢复步骤。
- 正式使用前必须完成一次完整恢复演练。

原机器为 Apple Silicon、16GB 内存、8 个逻辑核心，但系统盘空间不足，因此正式实施转移到新 Mac。新机器必须重新执行硬件、磁盘和容器环境预检；安装前至少保留 30 GiB 可用空间，再选择并安装适合 Apple Silicon 的容器运行环境。

## 17. 验收标准

- 缺少硬性交付物的项目不能正常通过阶段门。
- 自动排程不移动已锁定安排。
- 拍摄时间冲突、地点交通冲突和后期产能过载能够被识别。
- Timefold 不可用时仍可手工排程。
- 数据变化后的旧排程方案不能应用。
- D2 前后日历方案只能完整应用或完整回滚。
- 强制冲突必须记录原因并持续提醒。
- 客户增项保留原始基线并生成当前预测。
- 标准费率变化不修改历史成本。
- 项目关闭能够生成计划与实际复盘。
- 一次性导入在写入前显示差异，且不会自动删除数据。
- 备份能够恢复项目、人员、档期、成本和附件。
- 所有服务仅能从本机访问。

## 18. 被否决的方向

- 继续美化原 HRPM：没有升级管理模型，维护价值低。
- ERPNext 作为第一阶段主系统：财务能力强，但项目组合、阶段门和资源治理需要更多定制。
- Plane、Kimai 和 Timefold 三套系统并行：界面现代，但主数据同步和本机资源成本过高。
- 多套系统各自保存项目和人员：会产生冲突来源，无法判断哪份数据有效。
- 自动排程直接写入：不符合人工决策要求，也增加错误影响范围。

## 19. 上游与许可证管理

- 固定 OpenProject 和 Timefold 的具体版本，不跟随浮动 `latest` 标签。
- 保存上游仓库、版本、提交号、许可证和本地修改记录。
- 保留 GPL-3.0、Apache-2.0 及第三方组件要求的许可证声明。
- OpenProject 核心升级与 Video Operations 插件升级分开验证。
- 不把来自不同项目的源码直接复制到同一个模块；通过插件、依赖和本机 API 保持边界。

本设计不是法律意见。实现和分发时应继续保留上游许可证与版权声明。
